# 提案：消息批处理（窗口）

状态：提议（未实施）。前序：`docs/pipeline-review.md`（问题与取舍）、`docs/proposals/plugin-extension.md`（扩展面）。

## 1. 结论先说

**批处理不是扩展点，是时间轴上的分组。** 它不该做成第 6 个钩子（`on_batch`），也不该进 IR，
更不该让插件自己起线程攒消息。它应该长在「每会话有序流」上，表现为一个**分组策略**：

```
intake → 每会话有序流 → [窗口：决定何时封口] → 路由 → 出站队列
```

这个定位有一个直接好处：如果先建了每会话串行执行器（评审建议 7），窗口大约 80 行；
反过来先做批处理，会先造一套私有缓冲队列，再和串行执行器打架，最后合并两套排序逻辑。

## 2. 先把"批处理"拆成四种

这个词混着四种完全不同的需求，归属层也不同。混在一起做，就会做出一个万能但没人会用的机制。

| # | 需求 | 形态 | 归属层 |
|---|---|---|---|
| 1 | 刷屏合并 / 长消息分段到达 | 800ms 内的 N 条 → 1 个事件 | 管线：入站窗口 |
| 2 | 定时汇总（群聊摘要、热榜） | 每 60s 把窗口内容交给一次处理 | 管线：窗口 + 定时器 |
| 3 | 少发几次请求（限流/防刷屏） | N 条回复 → 1 条；长回复 → N 条 | 出站队列 |
| 4 | 跨会话批量推理（省钱） | 多个会话凑一批调一次模型 | **provider 层**，不是管线 |

第 4 种常见于"批量 API"（各家厂商都有 batch endpoint），但它的前提是放弃逐会话实时性，
且会话语义要在 provider 边界重新定义。**把它放进管线是错的**——管线不该知道"为了省钱我攒了三个群"。

真正需要改架构的只有第 1、2 种；第 3 种是发送器的事；第 4 种不进这条链。

## 3. 为什么不能放在别处

**放适配器**：适配器只做平台翻译，不知道"这是不是命令、该不该合并"。业务策略下沉到适配器，
接第二个平台就要重写一遍策略。否决。

**做成钩子**：钩子由「一个事件到达」触发，而批处理要「扣住一个事件，之后合成一个新事件」。
这是控制流原语，不是扩展点。硬做成 `on_batch` 会让钩子表里出现一个语义与其余五个都不同的成员。否决。

**放在插件里**：插件自建 `threading.Timer` 攒消息，热重载时无人回收（`on_unload` 也救不了已泄漏的线程），
且多插件各攒一份、各刷各的，顺序无法协调。否决。

## 4. 策略参数：两个上界是硬要求

```yaml
window:
  enable: true
  key: chat              # 按会话聚合
  trigger: debounce      # debounce（静默触发）| interval（固定节拍）
  ms: 800                # debounce 的静默时长
  max_count: 10          # 攒够 10 条立即封口
  max_wait_ms: 3000      # 首条到达后最多等 3s
  bypass: [command, at_bot, private]
```

**`max_count` 与 `max_wait_ms` 不是可选项。** 纯 debounce 在持续刷屏的群里永不触发——
每条新消息都把静默计时器重置，窗口一直不关，机器人从此不吭声。这是 debounce 的经典饿死陷阱，
而且症状是"越热闹越不回"，很难和"LLM 卡住"区分开。两个上界分别兜住"消息太多"与"消息太密"。

## 5. ctx：加字段，不加事件类型

批处理**不产生新的信封类型**。合成事件的文本按现有约定拼接（`_llm_text` 已经带说话人前缀），
另外把原件放进 `ctx["messages"]`：

```python
ctx["text"]         # "A: 早\nB: 早啊\nC: 这游戏真好玩"  —— 默认无感，存量插件不用改
ctx["messages"]     # [{"sender_id":..., "text":..., "message_id":...}, ...]  原件
ctx["batched"]      # True，方便需要精确处理的插件分流
```

这是有意的：**批处理对绝大多数插件应当是不可见的**。只有需要逐条处理的（命令匹配、精确计数）
才去读 `messages`。做成"新事件类型"会逼所有插件处理两种情况。

## 6. 旁路：命令不能被批

分类必须发生在窗口**之前**，且必须便宜（不调插件）：看首字符前缀、看 `mentions_bot`、看私聊。
命中 `bypass` 的消息不进窗口，直接投递。

代价是"分类规则"要在窗口之前维护一份，与命令插件的解析规则有耦合。控制办法：前缀表放配置，
命令插件声明自己的前缀（`PREFIX = "/"`），宿主聚合。若嫌麻烦，第一版只支持"私聊与 @机器人 不批"，
剩下的靠 `max_wait_ms` 兜底——命令被合进批次时最多延迟 800ms，不会丢。

## 7. 顺序：旁路消息必须先 flush

**这是最容易写错的地方。** 假设：

```
t=0   普通消息 M1 进窗口（待封口）
t=100 命令 M2 命中 bypass，直接投递 → 执行
t=800 窗口封口，M1 才被处理
```

结果是机器人先执行了 M2，后看见 M1——顺序反转。用户视角是"我还没说完它就动手了"。

正确做法：**旁路消息到达时先 flush 当前窗口，再投递自身**，两者都走同一个每会话串行执行器，
顺序由执行器的 FIFO 保证，不靠时间戳补。窗口在这里只做"分组"，绝不改变投递顺序——
这是把窗口挂到每会话流上、而不是让它自己持有队列的根本原因。

## 8. 出站的两个方向

出站队列同样涉及"批量"，但方向相反，别混成一个开关：

- **合并**：300ms 内的多条回复合成一条（防刷屏、省配额）。要求重试带幂等键，
  否则一次超时重试会把合并好的消息发两遍。
- **切分**：长回复按平台上限拆条（QQ 约 4500 字）。当前适配器侧未见长度处理
  （`translate_out.go` 无相关逻辑），超长回复由平台自行拒绝或截断——这属于出站队列的职责，
  不该让每个插件自己数长度。

## 9. 不做什么

| 不做 | 原因 |
|---|---|
| 通用流处理 DSL（window/join/aggregate 组合子） | 两种策略（debounce / interval）覆盖已知全部需求 |
| `on_batch` 钩子 | 语义与其余钩子不同类，属于控制流 |
| 让插件自建定时器攒消息 | 热重载泄漏线程，多插件各攒各的无法协调 |
| 跨会话批处理进管线 | 属于 provider（厂商 batch API），会打破会话隔离 |
| 窗口持久化 / 重启恢复 | 批次是瞬时的，重启丢一批可接受；退出时 flush 一次即可 |
| 可见性超时之外的重试语义 | 批处理不需要 at-least-once，别引入确认机制 |

## 10. 验收

1. 群里连发 5 条，机器人回 1 次（而非 5 次），且回复里能看到 5 条内容与说话人。
2. 持续刷屏 10s：`max_wait_ms` 到点必须封口，不能一条不回。
3. 批次待封口时发一条命令：命令在该批**之后**执行（顺序不反转）。
4. 关掉 `window.enable`，行为与现在完全一致（零回归）。
5. 存量插件不改一行代码也能正常工作（验证"批处理默认不可见"）。

## 11. 与既有建议的关系

窗口依赖评审建议 7（每会话串行执行器）。若暂时不做 7，最小实现可退化为：
**在 worker 内部按 chat 维护 `(待封口缓冲, 上次到达时间)`，dispatch 前判断是否封口**，
不引入独立线程。这版能跑，但 flush 时机受 worker 是否空闲影响，`max_wait_ms` 会有抖动——
作为过渡可以接受，长期仍应并入串行执行器。

批处理同时是背压手段：N 条变 1 条，下游负载直接降一个量级。它与评审建议 3（统一背压）
是同一问题的两种解法，实现时不要各做一套。
