## 🟡 中优先级

### 2. Stop 不等 goroutine 退出，与 spawn 竞争可孤儿化适配器子进程

- [x] **位置**：`internal/core/core.go:256-266`（Stop：cancel + killRuntime，
  不 join run/consume）、`internal/core/core.go:162`（spawn 完成后 Store 新
  runtime，不检查 ctx.Err()）
- **问题**：Stop 撞上 run() 的 spawn 执行中时（退避重启路径 core.go:168-192），
  spawn 不看 ctx 就把新 client 换进 runtime，而 killRuntime 已经跑完——
  新拉起的适配器子进程无人认领。DLL 宿主是长活进程，该孤儿会带着 WS
  重连循环一直活着。与 26101801#9（LoquatStart CAS 复位窗口）相邻，但那是
  启动侧、这是关闭侧，修法不同
- **修法**：run/consume 用 WaitGroup 收口，Stop 在 killRuntime 后 Wait
  （带超时防卡死）；spawn 完成后、Store 前补一次 ctx.Err() 检查，
  已取消则直接 Kill 新 client 不入册
- **验证**：扩展 core_race_test 场景——RestartAdapters 与 Stop 并发轰，
  结束后无存活适配器子进程（go-plugin 客户端全部 Closed）；-race 下无新告警
- **状态**：✅ 已完成（2026-10-22）：三层关死孤儿窗口——
  ① `runtimeMu` 串行化 spawn 换装与 killRuntime（Stop 杀完旧的，
  飞行中的 spawn 不可能再把新实例插到身后）；② spawn 入册前锁内复查
  ctx.Err()，已取消则 Kill 自己不入册；③ run/consume 挂 WaitGroup，
  Stop 在 killRuntime 后 Wait（5s 超时防卡死）。Status 顺带暴露
  adapter_pid。新测试 TestStopDuringRespawnNoOrphan：收集生命周期内
  出现过的适配器 PID，Stop 返回后逐一探活（Windows tasklist / Unix pgrep），
  实测全部退出；-race 全绿
- 提交：本次提交

### 3. NapCat 写路径无 deadline 且持锁写网络

- [x] **位置**：`cmd/adapter-napcat/napcat.go:247-255`（writeJSON 持 mu 调
  WriteJSON，全程无 SetWriteDeadline；对照读路径 napcat.go:104/106 有
  deadline，读写不对称）
- **问题**：对端 TCP 半死（NapCat 挂起、WSL 网络异常）时写无限阻塞且握着锁，
  connectLoop 重连路径同样要拿这把锁（napcat.go:72）——整个适配器僵死，
  之后核心只会按退避不停重启一个注定僵住的子进程
- **修法**：writeJSON 写前 `SetWriteDeadline(time.Now().Add(10s))`（时长收进
  顶层常量或配置）；写失败主动 Close 让读循环走既有的重连与 failPending 语义
- **验证**：手测或单测：对端 accept 后不读，写方 10s 内返回超时错误并触发重连，
  不再无限阻塞
- **状态**：✅ 已完成（2026-10-22）：writeJSON 写前 SetWriteDeadline
  （常量 10s，NapCat.writeDeadline 字段测试可缩短），写失败主动 Close
  让读循环走既有重连与 failPending 语义。单测 TestWriteJSONTimesOutAgainstStalledPeer：
  本机 httptest WS 服务端 upgrade 后 select{} 挂死，循环写 4MB 帧填满 TCP
  缓冲，300ms deadline 内返回错误，不再无限阻塞；-race 全绿
- 提交：本次提交

### 4. Go 侧零 recover，DLL 内 panic 直接炸宿主进程

- [x] **位置**：`internal/core/core.go:222-231`（consume 调 c.onEvent 宿主回调）、
  `cmd/` 与 `internal/` 全目录（grep 无任何 recover()）
- **问题**：panic 跨 C 边界 = 宿主进程 abort。Rust 侧有 R3 规则禁 unwrap、
  worker 池有 catch_unwind（src/main.rs:122），Go 侧却裸奔：onEvent 是宿主
  注入的不可信回调，consume/run/pump 任何一处 panic 都让整个机器人陪葬。
  跨语言防护不对称
- **修法**：consume 的 onEvent 调用处、run 循环体、pump 各包一层 recover
  （记日志后继续循环）。不需要通用 recover 框架，三个点足够
- **验证**：临时在回调里 panic，宿主只丢一条事件并打错误日志，进程不退；
  还原后 check-arch 与测试全绿
- **状态**：✅ 已完成（2026-10-22）：guard(logger, where) 助手包三处——
  consume 的 onEvent（宿主不可信回调，最关键）、run 的 pump 调用、
  pump 的 stream.Recv；panic 记 Error 日志（含 debug.Stack）后循环继续。
  新测试 TestConsumeSurvivesOnEventPanic：回调首条 panic，第二条照常投递；
  -race 全绿
- 提交：本次提交

  （SendAction/Status/SystemStatus）与 LogPipe fd 的归属；LoquatLogPipe
