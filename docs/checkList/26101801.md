## 背景：内存排查结论（实测记录，非待办）

用户观察的两个现象均已定位，**均非采集 bug，也非泄漏**：

### 1. 「和系统显示差挺多」= 口径不同

同一时刻的 loquat.exe 三口径实测：

| 口径 | 实测 | 对应工具/字段 |
|------|------|---------------|
| 专用工作集 | 28.8 MB | 任务管理器默认「内存」列 |
| 总工作集 | 49.3 MB | status 的 `host_rss_mb`（gopsutil `WorkingSetSize`） |
| 提交大小 | 812.0 MB | 任务管理器「提交大小」列（gopsutil `PagefileUsage`） |

- `host_rss_mb`（status.go:71）是总工作集，含三运行时映射的全部共享 DLL 代码页（实测共享 20.4 MB），比任务管理器默认列偏大 ~70%
- `go_heap_mb` 取 `ms.HeapAlloc`（活跃堆对象），不含 Go 栈/元数据/未归还页及 Rust、Python 内存，当「Go 堆」看是对的，当「Go 占了多少」看必然对不上
- 除数 `1e6` 是十进制 MB，任务管理器按 MiB 显示，固定 ~5% 偏差
- 提交≠占用：提交是配额承诺，物理压力只看工作集。日常看健康盯工作集（49.3 MB）即可

### 2. 「缓慢增加」= 高水位，非泄漏

逐环节排查全部排除泄漏：

| 环节 | 结论 | 证据 |
|------|------|------|
| Go 采集调用（host.Info / VirtualMemory / cpu.Percent / MemoryInfo） | 不泄漏 | 各循环 200 次后强制 GC，HeapAlloc 差值为负 |
| FFI 边界（C.CString ↔ LoquatFree） | 配对正确 | `take_c_string`（src/ffi.rs:125）转换后必调 free |
| Python 渲染（Pillow + gc.get_objects） | 高水位会饱和 | 模拟渲染 60 次，工作集 +2.3 MB 后持平 |
| 插件热重载 | 有清理 | 旧模块从 sys.modules pop（src/pluginload.rs:67） |
| chat 会话历史 | 有上限 | 每会话 `history_limit` 条 |
| 空闲的 loquat.exe | 完全稳定 | 114 s 采样，工作集/专用/提交纹丝不动 |

缓涨机制：Go GOGC 使堆按台阶向 OS 多要内存、归还慢；Windows 工作集用过的页不主动 trim；每次状态渲染重复加载字体（见 #5）推高 CPython 水位。均为「涨上去不下来、会饱和」，重启即归零。

812 MB 提交的定位：VirtualQueryEx 枚举显示 806.7 MB 集中在 `0x01b9xxxxxxxx` 段的 65 个 ~32 MiB 等大分配区——Go heap arena 地址签名，其余全部仅 ~5 MB。即历史上某次堆高峰（进程久跑，不可考）顶高 HeapSys，活跃堆早已缩回。探针实测：纯 Go 程序堆高峰 175 MB 后空闲静置约 40 s 即归还到 18 MB；loquat 因 gRPC 心跳持续活动归还不积极，属正常。

### 3. 0.5 GB Linux 轻量机评估

Linux 对本架构更友好（默认 overcommit，Go 堆水位不占硬配额；MADV_FREE 压力下自动回收）。账本：

| 组成 | RSS 估算 |
|------|----------|
| 系统底座（最小化 Debian/Ubuntu） | ~100 MB |
| **NapCat 本体（Node.js）** | **~150–300 MB，真正的大头** |
| loquat 宿主（Windows 实测平移） | ~50–60 MB |
| adapter-napcat 子进程 | ~15 MB |

合计 320–480 MB：**能跑但很紧**，NapCat 处理图片峰值最易触顶。必要措施：加 1–2 GB swap；给 Go 核心设 `GOMEMLIMIT`（如 64 MiB）。跨平台障碍见 #3。

## 🔴 高优先级

### 1. 消息处理全串行，一次 LLM 调用阻塞整条管线

- [x] **位置**：`src/main.rs:121`（主循环）→ `business.handle`（同步调用）→ `extensions/chat/plugin.py`（LLM 请求，`timeout_seconds` 默认 60）
- **问题**：主循环同步等 Python 业务返回。一条消息触发 LLM 调用期间（最长 60 s）：后续所有 QQ 消息排队、**控制台命令同样无响应**（`status`/`exit` 都敲不动）、群聊第二人干等。单核小机器上雪上加霜
- **修法**：回复路径异步化——每条消息交工作线程处理，回包在 worker 内独立走 `send_action`；控制台命令保持与主循环同通道即可恢复响应。注意 chat 插件的 `_histories` 并发保护（改锁或按 chat_id 分队列）
- **验证**：私聊触发一次慢 LLM（人为加 sleep），期间群里再发消息能正常响应、控制台 `status` 即时返回
- **状态**：✅ 已修复（2026-10-21）
  - 事件处理挪出主循环：chat_id hash 到 4 个 worker（每 worker 有界队列 64，满则丢+日志），
    worker 内直接走 `send_action` 发回复（CoreDll Send+Sync，Go 侧导出并发安全）；
    控制台命令保持主循环原地处理，响应恢复
  - 同一 chat 恒在同一线程串行：插件模块级状态（如 chat `_histories`）无需加锁；
    worker 带 catch_unwind，单条消息 panic 不死线程
  - 这是 agent 会话引擎的第一步，设计见 docs/agent.md
  - 已验：`cargo clippy -- -D warnings` 全绿、`cargo test` 11 通过（含 FFI 集成测试）；
    慢 LLM 场景的端到端验证待连接 NapCat 后人工复测
  - 提交：本次提交

### 2. 消息静默丢弃无日志

- [x] **位置**：`src/main.rs:49`（`parse_incoming`）与 `src/main.rs:125`（主循环 `let Some(...) else { continue }`）
- **问题**：OneBot 事件任一字段缺失即返回 None，主循环无日志 continue。OneBot 出新消息类型（如临时会话 `message_type: private` 但缺 `user_id` 路径、future 新类型）时消息无声消失，排查会很痛苦
- **修法**：`parse_incoming` 返回 `Result` 或在返回 None 的每个分支打一行 `eprintln!`（含 post_type / message_type 与截断后的原始 JSON）

- **状态**：✅ 已修复（2026-10-21，随 #1 顺手处理）：`parse_incoming` 意外分支

### 3. 跨平台硬编码（Linux 部署的前置障碍）

- [ ] **位置**：
  - `src/main.rs:82` —— `CoreDll::load("bin/core.dll")` 写死 Windows dll 名（Linux 产物为 `libcore.so`）
  - `Makefile:44-46` —— build 目标 `.exe` / `.dll` 产物名写死
  - `extensions/status/plugin.py:22` —— `FONT_CANDIDATES` 全为 `C:/Windows/Fonts/*`，Linux 退化为 Pillow 位图字体，**状态卡片中文全变方块**
  - `extensions/status/plugin.py:75`（`_to_wsl`）—— WSL 路径转换在 Linux 上多余（无害）

- **修法**：dll 路径按 `cfg!(windows)` 或配置项选择；Makefile 按平台出产物名；字体候选追加 Linux 常见路径（`/usr/share/fonts/...` 的 Noto Sans CJK / WenQuanYi）；`_to_wsl` 直接返回原路径即可
- **验证**：Linux 虚拟机/容器内 `make build` + 跑通 ping→pong + 状态卡片中文正常显示

## 🟢 低优先级

### 4. cpu.Percent 阻塞采样 200 ms

- [ ] **位置**：`internal/core/status.go:46`
- **问题**：每次状态查询固定阻塞 200 ms 以上（还有 ReadMemStats 的短暂 STW），QQ 发「状态」到出图明显偏慢
- **修法**：后台 goroutine 周期采样（如每 5 s 一次）缓存最近值，`collectStatus` 直接取；或非阻塞模式（interval=0，用上次调用以来的差值）
- **验证**：连续查询两次，第二次 <10 ms 返回且 CPU 百分比有值

### 5. status 插件字体无缓存，每次渲染从磁盘加载 8 次

- [ ] **位置**：`extensions/status/plugin.py:36`（`_font`），`_render` 每行调用一次 `_font(27)`
- **问题**：每次渲染从磁盘加载解析微软雅黑 8 次（标题 1 + 每行 1），渲染慢且推高 CPython 内存水位
- **修法**：`functools.lru_cache` 装饰 `_font`（或模块级 dict 缓存）
- **验证**：连续两次渲染，第二次耗时显著下降；内存水位不再随查询次数上涨

### 6. status 内存口径可与系统工具对齐（体验优化）

- [ ] **位置**：`internal/core/status.go:85-97`（payload）与 `extensions/status/plugin.py:108`（展示文案）
- **问题**：`host_rss_mb` 是总工作集口径，用户拿任务管理器对比必困惑（见背景 §1）；`go_heap_mb` 易被误读为「Go 占用的内存」
- **修法**（三选一或组合）：① 展示文案注明「总工作集，含共享库」；② 增加 `host_commit_mb`（gopsutil Windows 下 `MemoryInfo().VMS` 恰为 PagefileUsage，对应任务管理器「提交大小」列）；③ 顺带输出 `go_heap_sys_mb` 让虚/实可对照。另可选：暴露 `debug.FreeOSMemory()` 为控制台命令，一键验证归还
- **验证**：状态卡片数字可与任务管理器对应列互相印证

### 7. gc.get_objects() 每次查询构造数十万元素临时列表

- [ ] **位置**：`extensions/status/plugin.py:121`（`_py_objects`）
- **问题**：`gc.get_objects()` 返回全部跟踪容器对象的列表，开销大，且「跟踪对象数」不含 int/str 等非容器，作为「Python 对象数」展示有误导
- **修法**：换成轻量指标（如 `sys.gettotalrefcount` 仅 debug 版可用，改用 `tracemalloc` 峰值或直接删掉该行）
- **验证**：渲染耗时下降，卡片信息不误导

### 8. loquat_cfglib.resolve 每条消息重跑

- [ ] **位置**：`extensions/chat/plugin.py:45`、`extensions/qa/plugin.py:23`（每次 handle 都 resolve）
- **问题**：SCHEMA 校验 + 默认值回填每条消息执行一遍，配置不常变；类型不符时还会每条消息刷一次告警 print
- **修法**：宿主在 config 注入/热重载时 resolve 一次挂到模块属性，插件直接读；或插件内按 `id(config)` 缓存结果
- **验证**：类型不符的配置只告警一次

### 9. LoquatStart 的 CAS 复位存在并发窗口（理论瑕疵）

- [ ] **位置**：`cmd/core/dll.go:37-57`
- **问题**：spawn 失败时 `started.Store(false)` 复位，若与另一次并发 Start 交错，理论上可能双实例。当前 Rust 侧只在启动时调用一次，实际不触发
- **修法**：失败路径不复位（dll 生命周期本就进程级一次）；或复位前再持锁双检
- **验证**：代码 review 确认单次调用路径不变；并发场景属理论推演，不强求实测
