# 消息管线评审：架构、抽象层次与工程风险

> 评审对象：当前仓库的消息处理主链路（适配器 → Go 核心 → Rust 宿主 → Python 业务 → 出站）。
> 对比基线：Koishi（TypeScript / Cordis 依赖注入）、AstrBot（Python / asyncio 事件总线）。
> 方法：通读源码 + 本地实测关键热路径开销（Windows，12 个插件目录）。

---

## 一、现状

### 1.1 实际链路

```
平台 (NapCat)
  │ OneBot 11 / WS
  ▼
adapter-napcat（独立子进程，Go）
  │ 翻译为 IR（Segment oneof），chan 256，满则丢
  │ gRPC / yamux（hashicorp/go-plugin）
  ▼
core.dll（Go，c-shared，链在宿主进程内）
  │ 单 consume 协程：proto → protojson.Marshal → onEvent 回调
  │ chan 256，满则丢（eventsDropped 计数）
  │ C ABI（函数指针 + JSON 字节）
  ▼
Rust 宿主主循环（单线程）
  │ serde_json 解析 → 打日志 → 推 WebUI → chat_id 哈希选 worker
  │ mpsc 无界（事件与控制台命令共用）
  ▼
worker ×4（sync_channel 64，try_send 满则丢，无计数）
  │ business.handle()：先全量扫插件目录（写锁）→ 责任链按优先级首个非空接管
  │ pyo3 + GIL：ctx dict → json.loads(segments)
  ▼
Python 插件（LLM 最长 60s/轮 × max_turns 6）
  │ 返回 list[str]
  ▼
回到 worker：同步 FFI SendMessage（超时 15s，不重试）→ 发出去
```

### 1.2 关键参数（现状事实）

| 项 | 值 | 位置 |
|---|---|---|
| 适配器事件队列 | 256，满即丢 | `cmd/adapter-napcat/napcat.go` |
| 核心事件队列 | 256，满即丢 | `internal/core/core.go:27,297` |
| 宿主主队列 | **无界** | `src/main.rs:115` |
| worker 数 / 每 worker 队列 | 4 / 64，满即丢 | `src/stats.rs:14-16` |
| 会话内串行保证 | chat_id 哈希定 worker | `src/main.rs:209-214` |
| 出站发送 | worker 内同步阻塞，15s 超时，0 重试 | `src/main.rs:82` |
| 插件调用超时 | 无 | `src/business/mod.rs:279` |
| 插件加载检查 | **每条消息**全量扫描目录 | `src/business/mod.rs:129,280` |
| 回复类型 | `list[str]`（纯文本） | `src/business/mod.rs:303` |
| 去重 | 无（不按 message_id） | — |
| 限流 | 无（全链路） | — |

### 1.3 实测：热路径上的目录扫描

`business.handle()` 每条消息先调用 `sync()`，后者在读**写锁**内 `read_dir` 遍历 `extensions/` 下每个目录、`stat` 每个 `.py` 与 `config.yaml`。本机 12 个插件目录实测：

```
per-message scan: p50 = 2.32ms  → 单线程理论上限 ≈ 430 msg/s
```

由于 `sync()` 持有的是 `RwLock` 的**写**锁（`mod.rs:130`），4 个 worker 在此处完全串行 —— 并行度在入口处被抵消，吞吐上限不随 worker 数增长。这还没算上每条消息一次的 GIL 获取、segments 的 JSON 往返和一行 stderr 同步写。

## 二、对比分析

### 2.1 六维对照

| 维度 | Loquat 现状 | Koishi | AstrBot |
|---|---|---|---|
| **架构** | 微内核 + 驱动进程：适配器子进程隔离，核心/宿主/业务三运行时同进程 | 单进程全插件化，适配器也是插件 | 单进程 asyncio，适配器与插件同事件循环 |
| **抽象层次** | 入站 IR 完整（Segment oneof），**出站退化为字符串** | `h()` 元素树，收发同构 | `MessageChain`，收发同构 |
| **扩展性** | 目录约定 + 签名 + SCHEMA + 自动 install + 按插件热重载 | Cordis DI + service + 生命周期 dispose + 命令框架 | 事件管线阶段 + filter 装饰器 + 插件市场 |
| **性能** | 3 次序列化 + 3 次跨边界 + 每消息目录扫描 | 进程内对象直传，无序列化 | 进程内对象直传，async 并发 |
| **可靠性** | 适配器有监督/退避重启/panic 护栏；业务侧无超时无隔离 | 单进程，插件异常不隔离 | 单进程，handler 异常被捕获 |
| **可维护性** | 注释与决策记录优秀；三语言边界 + 无版本握手 | 类型系统统一，生态成熟 | 单语言，调试路径短 |

### 2.2 逐维判断

**架构 —— 最值得肯定，也自相矛盾。**
用 go-plugin 把适配器做成受监督子进程，配 per-platform 的 run 循环、指数退避、双端 panic 护栏（`core.go:233`、`main.rs:154`），这一层比 Koishi / AstrBot 都稳：适配器崩了只丢它自己那条流。`mvp.md` 也写明了原则——“隔离单位按变更频率和信任度划”。

但实际隔离恰好划反了：适配器是**自家稳定代码**，拿到了子进程；Python 业务插件是**变更最频繁、可信度最低**（代码由 AI 生成、随时热重载）的部分，却跑在宿主进程内，无超时、无沙箱、无资源上限。一次 C 扩展段错误即全进程陪葬，连 Go 核心一起带走。这是整套设计里最深的不一致。

**抽象层次 —— 入站一流，出站断层。**
IR 设计是克制的：只有 ≥2 个平台有的概念才进 IR，单平台走 `extension`，编号留白（`adapter.proto:87`）。这个判断标准比多数同类项目成熟。

问题在出站：`handle()` 返回 `list[str]`，宿主把每个字符串包成单个 text 段（`main.rs:81`）。于是**入站能收到 at/图片/引用，出站只能回纯文本**。想发图/引用/at，只能走逃生舱 `core.send_action()`（`pybridge.rs:47`，`chat/plugin.py:194`）—— 而逃生舱完全绕过出站统计、排序与（未来会有的）限流，等于在管线旁边开了条无管制的小路。Koishi 的 `h()` 和 AstrBot 的 `MessageChain` 收发同构，没有这个断层。

**扩展性 —— 本地开发体验好，组合能力弱。**
目录约定 + 首行签名 + `SCHEMA` + `install/enable` + 按 mtime 热重载，这套 DX 相当顺手，比 AstrBot 的配置体系更轻。但组合原语太少：

- 责任链是**路由器**不是管线：首个返回非空的插件独占消息，没有 `next()`、没有 before/after 钩子。横切关注点无法表达——最典型的是 `chat` 插件的 `observe()`：未触发的群消息靠它记历史，但只要 `qa` 或 `status` 先接管了，这条消息就永远不进历史（`chat/plugin.py:252`）。这是"首个接管"语义直接导致的语义缺陷。
- 无命令框架（参数解析/别名/前缀），每个插件自己 `split()`。
- 无服务注册与注入：provider 是启动时快照，加一个平台/LLM 通道要改 YAML 重启。
- 无 `PLUGIN_API_VERSION`，宿主改 ctx 字段时插件静默失败。

**性能 —— 边界税高，且热路径上有磁盘 I/O。**
一条消息从平台到插件经历了：平台 JSON → protobuf → protojson 字节 → `serde_json::Value` → 再序列化成 JSON 字符串 → Python `json.loads` 成 dict。四次序列化、两次跨语言拷贝（`on_event` 里 `to_vec()`）。Koishi/AstrBot 是对象直传，零序列化。

单看单条开销（几十 µs 量级）尚可接受，真正卡住的是那条 2.3ms 的目录扫描 —— 它把理论吞吐压到 ~430 msg/s，而 worker 池的并行度在这一步被写锁抹平。

**背压 —— 三处独立丢弃，互不知情。**
adapter 256 丢 → core 256 丢 → worker 64 丢，加上一条**无界**的宿主主队列。四种语义混在一起：

- 无界队列（`main.rs:115`）是隐患：主循环若被控制台命令或 WebUI 阻塞，内存无上限增长。
- 只有 Go 侧的 `eventsDropped` 进了 `/status`；worker 侧丢弃只有一行日志，无计数、无指标。
- 丢弃对用户完全不可见 —— 被丢的私聊用户永远等不到回复，也没有"忙"的降级回复。
- 无准入控制，无每会话队列上限：一个热门群可以吃满某个 worker 的 64 格，同桶的其他会话全部饿死。

**可靠性 —— 有真功夫，但缺关键两块。**
做到位的：适配器退避重启、panic 双端护栏、毒锁恢复（`recover_poison`）、每条消息 `catch_unwind`、发送失败识别 `{"error"}` 信封（`main.rs:101`）。这些细节说明作者踩过坑。

缺的两块：**超时**与**去重**。

- 无插件超时。`max_turns=6` × 60s LLM 超时 = 单条消息最长 360s 占住 1/4 容量（`agent.py:123`）。更糟的是 GIL：任何插件里的纯 Python 死循环会冻结全部 4 个 worker，"4 个 worker"的并行假象瞬间归零。
- 无 message_id 去重。适配器重连、上游重试、人工补发都可能重复投递，直接导致重复回复（LLM 场景下就是重复计费）。
- 出站零重试。`send_message` 失败只记一行日志（`main.rs:94`），NapCat 限流（retcode 1200）时用户看到的是"机器人不理我"。
- LLM 零重试：`llm.py` 单次 `urlopen`，429/5xx/超时一律降级为 `None`，用户收到"（LLM 调用失败，详见控制台日志）"。
- 退出路径 `std::process::exit(0)`（`main.rs:177`），不 drain、不 flush，正在处理的会话历史可能丢掉最后一次写入。

**可维护性 —— 注释是加分项，语言边界是减分项。**
注释密度与决策记录（带清单编号）在同类项目里属于上游水平，读起来不费劲。代价是三语言 + c-shared ABI：

- 无 ABI 版本握手：`core.dll` 与宿主编译不同步时，错误表现为崩溃而非明确报错。
- FFI 契约是"protojson 的 camelCase 字段名"，靠约定维持；改个字段名，Rust 侧静默拿空串。
- 跨语言栈难追：Go panic 跨 C 边界直接 abort。

## 三、问题清单（按优先级）

### P0 — 直接限制正确性或吞吐，建议立即处理

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P0-1 | 每条消息全量扫描插件目录，且持**写锁** | `business/mod.rs:130,280`；实测 2.3ms | 吞吐上限 ~430 msg/s，worker 并行失效 |
| P0-2 | 加载失败的插件**每条消息重试编译** | `mod.rs:220`（失败不入册、无失败标记） | 语法错一个插件 = 每消息一次异常+traceback+日志 |
| P0-3 | 三处独立丢弃 + 一条无界队列，仅一处有计数 | `core.go:297`、`main.rs:115,216` | 消息静默丢失、内存无上限、故障不可观测 |
| P0-4 | 出站同步阻塞在 worker 内，无重试无限流 | `main.rs:82` | worker 被 15s 超时占住；平台限流即丢回复 |
| P0-5 | 插件调用无超时，GIL 使单插件可冻结全池 | `mod.rs:279`、`agent.py:123` | 单条消息 360s；死循环 = 全局停摆 |
| P0-6 | 出站只有 `list[str]`，结构化回复依赖逃生舱 | `main.rs:81`、`pybridge.rs:47` | 表达能力受限；旁路绕过统计/排序/限流 |

### P1 — 影响表达力与长期演进

| # | 问题 | 影响 |
|---|---|---|
| P1-1 | "首个非空接管"无法表达横切关注点 | 历史/审计/埋点会被高优先级插件截胡（`observe` 已中招） |
| P1-2 | chat_id 哈希定 worker，无每会话队列上限 | 跨会话 head-of-line blocking；热门群饿死同桶会话 |
| P1-3 | 无 message_id 去重 | 重连/重试导致重复回复、重复计费 |
| P1-4 | 会话落盘每条群消息全量重写 | `agent.py:94` 写入放大，磁盘 churn |
| P1-5 | 无 ABI / 插件 API 版本握手 | 版本错配表现为崩溃或静默空值 |
| P1-6 | 退出不 drain（`process::exit(0)`） | 最后一次历史写入可能丢失 |
| P1-7 | 可观测性只有计数，无延迟/分阶段/分级丢弃 | 性能问题只能靠猜（本次评审即如此） |

## 四、改进建议（可落地，按收益排序）

### 建议 1：把 I/O 移出热路径（P0-1、P0-2）

- `sync()` 改为**时间节流**（如 500ms 一次）或事件驱动（`notify` 监听目录），普通消息路径只读快照、只拿**读**锁。
- 加载失败的插件记入 `failed` 表并指数退避（如 1s→2s→…→60s），不再每消息重试。
- 验收：单消息管线开销 p50 < 0.1ms；`cargo test` 增加"坏插件不影响吞吐"用例。

> 改动量约 60 行，收益最大。这一条几乎单独决定了吞吐量级。

### 建议 2：出站队列化（P0-4、P0-6、P1-3）

worker 只负责"产出回复"，发送交给独立发送器：

```
worker → outbound queue（每会话 FIFO） → sender pool
                                        ├─ 每平台令牌桶（限流）
                                        ├─ 有限重试（指数退避 + 抖动，仅对可重试 retcode）
                                        └─ 幂等键 (platform, chat_id, client_msg_id)
```

- per-chat FIFO 天然保住会话内顺序（不再依赖"worker 内同步发送"这个副作用）。
- 逃生舱里属于"发送类"的 action（`send_*_msg`）也应汇入此队列，消除旁路。
- 验收：LLM 慢时 worker 占用时间不含发送耗时；限流场景下重试成功率可观测。

### 建议 3：一条有界管线 + 准入控制（P0-3）

- 宿主主队列改 `sync_channel(N)`，满时对 Go 侧形成反压（`pump` 的 `select` 已支持阻塞，只需去掉 `default`）。
- 丢弃统一到一处计数，分阶段打标（adapter/core/host/worker），进 `/status`。
- 私聊被丢时回一条"当前繁忙"的降级消息（需在丢弃点保留 chat 上下文）。
- 验收：`/status` 能回答"丢在哪一层、丢了多少"。

### 建议 4：执行预算与隔离（P0-5）

- 给 `handle()` 传 `deadline`（`ctx["deadline_ms"]`），LLM 总预算 = `min(max_turns × timeout, budget)`，超预算立即收尾返回部分结果。
- LLM 客户端加**一次**重试（仅 429/5xx/连接错误），带 200~800ms 抖动。
- 高危/重插件（LLM 对话）迁到独立 Python 子进程（复用现有 go-plugin 思路或 `multiprocessing` + 管道），与适配器一致的隔离级别。
- 验收：单插件死循环不再冻结其他会话。

### 建议 5：回复类型升级（P0-6）

`handle()` 返回值向后兼容地扩展：

```python
return "纯文本"                          # 旧写法不变
return [{"text": {"text": "看这个"}},
        {"image": {"url": "https://..."}}]  # IR 段，直接复用入站 schema
```

宿主侧把 `Vec<Value>` 直接序列化成 `SendMessageRequest.segments`，不再包成单个 text 段。
验收：发图/引用/at 不再需要 `send_action`。

### 建议 6：两阶段管线（P1-1）

保留"首个回复者接管"作为默认策略，但把链路拆成：

```
before(ctx)  → 全部执行（可标记 handled、可改 ctx、可记历史）
   ↓ 命中者产出 replies
after(ctx, replies) → 全部执行（审计、落库、WebUI 推送）
```

这样 `observe`/日志/埋点能无条件执行，`qa` 抢答也不丢历史。改动约为 `handle()` 内 30 行。

### 建议 7：每会话串行执行器（P1-2）

用 `HashMap<chat_key, VecDeque<Msg>>` + 全局就绪队列替代哈希分桶：同会话严格串行、不同会话不互相阻塞、每会话可设上限。这是把"顺序保证"从哈希的巧合变成显式契约，同时消掉 head-of-line blocking。

### 建议 8：可观测性最小集（P1-7）

只加四样，不要上 OpenTelemetry：分阶段计时（parse / chain / send）、各队列深度、分级丢弃计数、handler p50/p99。全部从现有 `stats.rs` 扩展，进 `/status` 与 WebUI。

### 建议 9：低成本的正确性补丁（P1-3、P1-5、P1-6）

- `(platform, message_id)` 去重，LRU + 5 分钟 TTL，约 20 行。
- 启动时调一次 `LoquatAbiVersion()` 比对；插件首行 `# loquat-plugin v1` 带版本。
- 退出改为：停收新事件 → drain worker → flush 会话 → `Stop()` → 返回 main。

## 五、过度设计：应当避免的

当前代码的克制感是优点，下列方向**不建议**做，投入产出比差：

| 别做 | 原因 |
|---|---|
| 持久化事件日志 / exactly-once / 可回放流 | 聊天场景 at-most-once + 可见丢弃足够；为此引入 WAL 与游标是负收益 |
| 引入 Redis / NATS / Kafka | 单机单进程机器人，中间件只增加部署与运维面 |
| 自研 actor 框架 / 协程运行时 / executor | 现有 mpsc + 线程池够用；换成 actor 是重写不是改进 |
| 多级优先队列 + 老化 + work stealing + 公平调度 | 先测量；在 ~430 msg/s 的现状瓶颈下，调度器不是瓶颈 |
| 每个插件独立进程 | 12 个插件 = 12 个解释器，内存与启动成本失控；只对单个高危插件做 |
| WASM / seccomp 沙箱 | 现阶段威胁模型是"自己写的插件"，不是多租户 |
| 通用消息元素 DSL / 任意嵌套树渲染器 | 扁平段列表已覆盖 95%；嵌套树是平台适配器该操心的 |
| 照搬 Cordis 的 DI 容器 / 内建 ORM | 那是 Koishi 多年演进的结果，抄形态抄不到收益 |
| 为了"架构纯粹"重写成单运行时 | 三运行时的成本已经付了，收益（适配器隔离）也是真的；该冻结而非重写 |

---

## 六、取舍权衡

| 决策点 | 现状选择 | 得到 | 付出 | 建议 |
|---|---|---|---|---|
| 运行时数量 | 三语言同进程 | 各取所长、适配器隔离 | 序列化税、跨语言调试 | **保留**，冻结 Go 核心职责 |
| 隔离边界 | 适配器子进程 / 业务进程内 | 适配器稳 | 最不可信的一侧无隔离 | **调整**：高危插件也隔离 |
| 背压策略 | 到处丢弃 | 永不阻塞、可用性优先 | 静默丢消息 | **保留丢弃，但必须可见 + 降级回复** |
| 责任链语义 | 首个非空接管 | 省算力、确定性 | 无横切、无组合 | **改为两阶段** |
| 会话顺序 | 哈希定 worker | 顺序免费获得 | head-of-line blocking | **改为每会话队列** |
| 出站抽象 | 纯文本 | 实现最简单 | 表达力受限、旁路滋生 | **升级为段列表** |
| 插件热重载 | 每消息惰性扫描 | 改代码立即生效 | 吞吐被封锁 | **改节流/监听** |

一句话总结取舍原则：**可用性优先于完整性（丢弃可接受）、显式优于隐式（顺序与隔离要写进契约）、表达力优先于实现简洁（出站必须与入站同构）**。

---

## 七、建议的推进顺序

1. **先测量**：按建议 8 加最小埋点，拿到真实 p50/p99 与丢弃分布（半天）。
2. **建议 1 + 9**：热路径去 I/O、失败插件退避、去重、版本握手、优雅退出（1~2 天，风险低）。
3. **建议 2 + 3**：出站队列化、统一背压（3~5 天，需改 FFI 契约）。
4. **建议 4 + 5**：执行预算、段列表回复（1 周，涉及插件契约升级，注意向后兼容）。
5. **建议 6 + 7**：两阶段管线、每会话执行器（1 周，纯内部重构）。

前两步做完，吞吐与可观测性就会有量级改善；后三步决定这套框架能否承载第三方插件。
